# 语音功能拆解（不用懂代码也能看完）

这篇只讲三件事：**用户点一下之后发生了什么**、**为什么每一步要那么做**、**你会遇到什么坑**。

不需要懂编程。

---

## 一、先看用户看到的东西

角色在正文里说一句话：

> 她抬起头看你。
>
> **“你来啦”** 🔘 ← 这句旁边有个小按钮，五根小竖条，像声波

点了那个按钮：

- 一两秒后，听到角色用自己的声音把这句话念出来
- 五根小竖条的动画跟着音量跳动
- 再点一次，**立刻**出声，没有等待

从没听过 → 点 → 等一下 → 能听
听过一次 → 再点 → 立刻响

**"第二次立刻响"就是整个语音系统最核心的设计目标。** 下面所有东西都是为了它。

---

## 二、点一下之后，背后跑了八步

用做饭打比方：**你在手机上点了一道菜，背后是"看冰箱 → 看有没有人在做 → 下单 → 装盘 → 上桌"。**

### 第 1 步：确认这个人有没有"嗓子"

先查这个角色配过音色没有。

- 没配 → 弹出提示"去角色里选一个音色"（不会报错，不会静默失败）
- 配了 → 往下走

> **为什么先查这个**：没配音色还往下走，一定会失败，但失败发生在 10 秒后，用户会以为卡了。**先查、快失败、给明确指引**，这是所有交互的铁律。

### 第 2 步：算一个"指纹"

把这次要合成的东西全部打包：

```
哪个引擎 + 哪个模型 + 什么音色 + 什么情绪 + 这句台词的原文
```

然后对这堆字算一个哈希值（一串固定长度的字符）。

这个哈希值就是这句台词的**身份证号**。

> **为什么要算身份证而不是直接用台词文本当名字？**
> 同一句"你好"，用不同音色念出来是不同的声音，不能共用。
> 同一句"你好"，用同一个音色但情绪是"开心"还是"生气"，也是不同的声音。
> 所以必须把"所有会影响声音的参数"都算进去。
>
> **为什么不直接用那堆参数当名字？** 太长了，没法当存储的键。

### 第 3 步：看冰箱

拿这个身份证号去查缓存（浏览器里的一个小数据库）。

- **有** → 直接把音频拿出来播。**这一步是 0 成本。**
- **没有** → 往下走

> **这就是"第二次立刻响"的实现。** 第一次花时间花钱，第二次以后全免费。
>
> 一句台词可能被点十次。缓存省下的不是 10%，是 90%。

### 第 4 步：看有没有别人正在做同一道菜

检查"正在制作中"的清单里有没有同样的身份证号。

- **有** → 等它的结果，不重复下单
- **没有** → 往下走

> **这个场景真实存在**：
> - 用户手快，连点两下
> - "提前生成"正在做第 3 句，用户这时点了第 3 句
>
> 不做这层，同一句话**付两次钱**。

### 第 5 步：下单（真正调 API）

把请求发给语音服务商（Fish Audio / MiniMax / ElevenLabs / 小米 / 火山…），等它返回音频文件。

这一步是**真正花钱和花时间**的地方，通常 1-3 秒。

### 第 6 步：装冰箱

拿到音频，用身份证号存进缓存。

同时更新一个"总占用"的计数，用来判断要不要清理旧文件（缓存有容量上限，超了就淘汰最久没听的）。

### 第 7 步：播

- 把音频数据解码成浏览器能播的格式
- 出声
- 同时分析音量，驱动那五根小竖条跳动

> **这一步有个技术限制**：iPhone 上，浏览器不允许"自动出声"，必须由用户的一次点击触发。所以第一次点的时候要"解锁"音频通道。

### 第 8 步：顺手把下一句也做了

在播这一句的同时，**已经开始做下一句**了。

> **为什么要提前做**：语音合成有 1-3 秒延迟。不提前做，用户听完一句、点下一句，又要等 2 秒。
> 提前做之后，用户点下一句是"立刻响"。
>
> 这个技巧叫"预取"，是所有播放器（音乐、视频、语音）的通用做法。

## 三、五个关键设计，每个都是钱买来的教训

### 设计一：缓存用"全参数指纹"，不用"台词文本"

| 做法 | 后果 |
|---|---|
| 用台词文本当 key | 同一句"你好"，换了音色还是放旧声音 → 用户以为换音色失灵 |
| 用全参数指纹 | 每个组合独立缓存，正确 |

### 设计二：三层存储，各管一段

| 层 | 存什么 | 位置 | 多大 |
|---|---|---|---|
| 热缓存 | 最近听过的几十条 | 内存 | 约 16 MB |
| 冷缓存 | 所有听过的 | 浏览器数据库 | 占配额 20% |
| 配额 | 总容量上限 | 由浏览器给 | 200MB–2GB |

**读的顺序**：内存 → 数据库 → 都没有才下单。

> **为什么分三层**：内存里的是"马上要用的"，速度快到没有延迟。数据库里的是"可能还会听的"，慢一点但存得多。都不在才花钱。

### 设计三：预取一句，不预取全部

- 播第 1 句时，做第 2 句
- 播第 2 句时，做第 3 句
- **不会**一次性把整段回复全做完

> **为什么**：整段做完，如果用户只听了第一句就走了，后面的全白花钱。
> 只提前一句，是"体验"和"浪费"之间最划算的点。

不过它还有一个模式叫"提前生成"：回复一出来，后台慢慢把整段做完，用户点哪句都是现成的。**这个模式会烧钱，所以默认关着，让用户自己开。**

### 设计四：情绪要"翻译"成每个引擎能懂的方言

这是整个语音功能里最脏的活。假设台词写着"开心"：

| 引擎 | 它要的写法 |
|---|---|
| Fish S2 | `[happy] 台词` |
| Fish S1 | `(happy) 台词` |
| Fish drama-3 | `[开心的语气说这句话] 台词` |
| 小米 MiMo | `(开心)台词` |
| MiniMax | 另一个字段里填 `emotion: happy` |
| ElevenLabs | 部分模型支持 `[happy]`，部分直接忽略 |

**而且中文情绪要先翻成英文**（"开心"→"happy"），因为多数引擎只认英文词。

> **这就是为什么它需要一整个单独的文件来干这件事。** 每接一个新引擎，就要研究它的文档、试出它能认哪些词、记下来。

### 设计五：动作不朗读

正文里经常有：

> “你来啦”**（她笑着把门推开）**

括号里的动作**不能念出来**。所以合成前要剥掉。

但是——**有些括号是台词本身的一部分**，比如“（小声）我不太舒服”。所以不能一刀切剥所有括号，要看上下文。

> 它在这里做了很细的判断：如果情绪字段是"心声"，那么前置的＊号或括号里的内容是"译文"，不是动作。

## 四、最难的部分不是合成，是"在正文里长出按钮"

你可能会想：不就是往文字后面加个按钮吗？

**不。** 因为正文不是它一个人管的。

### 真实情况

酒馆的正文渲染是这样的流水线：

```
模型输出的原始文字
    ↓
别的插件的美化正则（可能把整段包成卡片、加边框、改样式）
    ↓
上屏
```

如果你在第一步就插 `<button>`，被后面那层正则一包：

- 按钮可能被切成两半
- 或者被当成文字转义掉
- 或者落进代码块里，点了没反应

### 它的解法：分两次下手

**第一次（正则之前）**：不打真按钮，只打"隐形标记"

具体做法是把每句台词变成：

```
[看不见的标记] 第3行 [看不见的标记] “你来啦” [看不见的标记]
```

这些标记用的是 Unicode 里一段"没人用的字符"（私用区）。**在正则和 markdown 眼里，它们就是普通文字**，所以不会被切坏。

**第二次（正则之后）**：把隐形标记换成真按钮

这时候正则已经跑完了，卡片已经成型，再把标记替换成 `<button>`，就不会破坏结构。

**第三次（兜底）**：清理落错地方的按钮

如果某句台词正好落进了代码块里（用户手动贴了代码），那个位置插件的样式和点击都够不着 —— 于是把按钮拆掉，只留文字，保持原样。

> **这个"先打标记、等别人处理完再换成真东西"的思路非常值得抄。**
> 任何"要在别人的页面上加东西"的场景都需要它。

## 五、真实成本

| 项目 | 情况 |
|---|---|
| 免费额度 | 语音基本没有免费额度（画图有，语音没有） |
| 计费方式 | 按字符数或按次 |
| 一句台词 | 通常几厘到几分钱 |
| 缓存命中 | **0 成本** |
| 预生成 | 每句都花钱，是主要开销 |

**省钱的三条**：

1. **缓存**（最重要）—— 同一句只付一次
2. **只提前做一句**，不做整段
3. **预生成默认关着**，让用户自己选

## 六、你会踩的坑（按踩到的概率）

| 坑 | 症状 | 解法 |
|---|---|---|
| **iPhone 不出声** | 点了没反应，安卓正常 | 音频必须由用户点击触发；iOS 14.5 以下功能不全 |
| **跨域音频解不开** | 报错 `decodeAudioData failed` | 音频接口要允许跨域，或者自己转一道 |
| **中文情绪不生效** | 声音永远平淡 | 中文情绪要翻成英文；有些引擎压根不支持情绪 |
| **长文本合成失败** | 长台词经常报错 | 超长要切段（它用的阈值是 220 字左右，在句号处切） |
| **切到后台就停了** | 切标签页回来发现不播了 | 浏览器的省电策略，要监听 `visibilitychange` 恢复 |
| **缓存把手机塞满** | 用久了浏览器变慢 | 要给缓存设上限，超了淘汰最旧的 |
| **同一句付了两次钱** | 账单比预期高 | 要做"正在制作中"的去重 |

## 七、如果是我给你做，会怎么做

它那套是"大而全"：支持 5 个引擎、三种渲染路径、预生成、自动挑音色、音效处理。

**你的版本不需要一次做完。** 我建议分三步：

### 第一步：能响（1 天）

- 只接一个引擎（你常用的那个）
- 点击 → 合成 → 播 → 存缓存
- 不做预取、不做情绪、不做预览

做完的验收：点一下能听到声音，再点一下立刻响。

### 第二步：好用（1 天）

- 加预取（播这句时做下句）
- 加"正在制作中"去重
- 加缓存容量上限
- 情绪翻译（先只做你那个引擎的方言）

### 第三步：像样（2 天）

- 多引擎切换
- 波形动画跟着音量
- 缓存管理界面（看占了多少、一键清空）
- 失败重试和错误提示

**语音的难点从来不是"调 API"，是"缓存 + 去重 + 分段 + 渲染"这四件事。** 调 API 只占两成工作量。

---

## 八、一句话总结

> **语音功能的核心不是"让 AI 说话"，是"让同一句话只说一次钱，让第二次点没有等待"。**

想清楚这两件事，剩下都是接 API。
